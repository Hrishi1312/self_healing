Seven threads, one budget

One agent, one tool. The tool splits a user story into scenarios and runs every one of them at the same time — each on its own thread, each with its own repair loop. Below is a real run: story 640764, seven scenarios, 324 seconds. Run sequentially it would have taken 1,150.

THE SHAPEOne agent, one tool, three sub-agents

You run the agent at the top. It calls the tool once and hands back whatever the tool returns. Everything else — reading the story, splitting it, running seven threads, judging, repairing — happens inside the tool. The three sub-agents are not on the workflow canvas; the tool calls them by id.

ONE THREADWhat each scenario does on its own

Seven copies of this run at once. Nothing waits for anything else — a thread that passes first time finishes in 99 seconds while its neighbour is still on its second attempt.

  1. Generate. The test case agent gets one scenario and writes three test cases as nested JSON. 84–145s, the longest step by far. The tool expands the JSON into the 13-column table itself, so the model never repeats the nine header columns on every step row.
  2. Review. An independent judge scores every test case and marks each pass or fail. 15–26s. It returns one plain-English reason per failure alongside the precise evidence the generator needs.
  3. All passed? The thread stops. Its test cases are ready to use. Four of seven scenarios reached this on the first attempt — two scoring 95, one 100.
  4. Otherwise, repair. Only the failing test case ids go back, with the reviewer's quoted evidence. Three scenarios needed this. TS_002 went 85 → 95 and passed; TS_004 also recovered.
  5. No improvement? Stop. If the second score is no better than the first, the thread gives up rather than spending another two minutes. TS_003 scored 85 twice and stopped. Its test cases are still in the output, flagged for a human.

WHY IT FITSParallel or nothing

Generation is 80% of the cost and it happens once per scenario. Run those in sequence and the run is four times longer than the platform allows.

READING ITQuestions people ask first

Plain answers, no jargon.

What is a "thread"?

One scenario, doing its own work. Seven scenarios means seven threads, all going at the same time. Each one writes its test cases, gets them checked, and fixes them if needed — without waiting for the other six. That is why the whole run takes as long as the slowest thread, not all seven added together.

Why does nothing happen for the first 45 seconds?

Two jobs have to finish before there is anything to split up: reading the story from Azure DevOps (under a second), and turning it into seven scenarios (44 seconds). Only then does the work fan out. That 45 seconds is the same whether you ask for two scenarios or ten.

What is a repair round?

The reviewer said one of the three test cases was not good enough, so the thread writes them again — this time it is told exactly what was wrong. Three of the seven threads needed one. Two of those came back better and passed. A repair costs about two more minutes, which is why the lanes that needed one finish so much later.

One lane scored 85, then 85 again, and stopped. Why?

If a repair does not improve the score, trying a third time almost never helps — the generator has already seen the feedback and produced the same thing. So the thread gives up instead of spending another two minutes. Its test cases are still in the output, marked for someone to look at.

"20 of 21 ready" — is the other one missing?

No. You always get all 21. "Ready" means the reviewer had no objection and you can hand it to a tester as it is. The one that is not ready is in the same file, with a note saying what the reviewer did not like — in this run, wrong status for a negative-path test. It is a second opinion, not a filter.

Why is the review bar so much shorter than the writing bar?

Writing three test cases with fifteen steps each takes a while — 85 to 145 seconds. Reading them and giving a verdict takes 15 to 26. Writing is where nearly all the time goes, which is also why the threads matter: it is the writing that runs seven ways at once.

Would more scenarios make it slower?

Barely. Six scenarios and seven scenarios both take about five minutes, because they run side by side. What does make it slower is repairs — each one adds a full round of writing and reviewing to that one lane.

STAYING SMALLFive things that keep the payloads down

The first version of this pipeline sent everything in one call and kept dying. Each of these is measured, and each one bought back time or headroom.

01 The generator writes nested JSON, not a table. In the 13-column table, nine columns repeat identically on every step row — 65% of all characters were the same text over and over. Writing each test case once, with its steps as a list, and letting the tool build the table cut what the model has to produce from 27,819 characters per scenario to 15,724. Flat JSON would have been 36% worse than the table, because it repeats the key names instead. −43%
02 The finished table never goes back through an agent. It is printed to the log; the answer carries a pointer to it. Returning it meant the calling agent had to retype 53,000 tokens it already had — about fifteen minutes of doing nothing useful. 42× smaller
03 One scenario per call. Each generate call carries roughly 28 KB instead of all seven scenarios at once. The single-call version produced 124 KB in one response and the connection kept dropping. Smaller calls are also what makes them safe to run in parallel. 4× smaller
04 A repair is told which test cases are broken. The reviewer returns a verdict per test case, so the repair round gets the failing ids and the exact quoted evidence — not a single score for the batch and a request to start over. targeted
05 Submit, then poll. No request is held open while an agent thinks. The longest single call in this run took 227 seconds and returned normally, because the tool asked for the result rather than waiting on the line. no timeouts
