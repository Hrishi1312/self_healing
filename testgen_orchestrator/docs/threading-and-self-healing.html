Seven threads, one budget

One agent, one tool. The tool splits a user story into scenarios and runs every one of them at the same time — each on its own thread, each with its own repair loop. Below is a real run: story 640764, seven scenarios, 324 seconds. Run sequentially it would have taken 1,150.

THE SHAPEOne agent, one tool, three sub-agents

You run the agent at the top. It calls the tool once and hands back whatever the tool returns. Everything else — reading the story, splitting it, running seven threads, judging, repairing — happens inside the tool. The three sub-agents are not on the workflow canvas; the tool calls them by id.

ONE THREADWhat each scenario does on its own

Seven copies of this run at once. Nothing waits for anything else — a thread that passes first time finishes in 99 seconds while its neighbour is still on its second attempt.

  1. Generate. The test case agent gets one scenario and writes one test case per entry on its "Conditions to cover" list — one to six — as nested JSON. 63–145s, the longest step by far. The tool expands the JSON into the 15-column table itself and injects the seven constant columns, so the model never repeats the header columns on every step row. A single case returned as a bare object instead of a one-element array is wrapped and accepted on a first attempt — there is no table yet to lose.
  2. Review. An independent judge scores every test case and marks each pass or fail. 15–26s. It returns one plain-English reason per failure alongside the precise evidence the generator needs.
  3. All passed? The thread stops. Its test cases are ready to use. Three of seven scenarios reached this on the first attempt — 92, 92 and 96.
  4. Otherwise, repair. Only the failing test case ids go back, with the reviewer's quoted evidence. Four scenarios needed this. TS_003 went 85 → 92 and TS_005 went 85 → 95; TS_001 and TS_004 did not recover and shipped flagged.
  5. No improvement? Stop — and keep the best. If a repair improves neither the batch score nor the number of passing test cases, the thread gives up rather than spending another two minutes. Any failing case pins the batch score at 85, so the passing count is the signal that actually moves. Whatever round reviewed best is what ships: a repair that comes back worse is discarded (step=keptbest in the log), so a heal round can never lose work. The kept cases stay in the output, flagged for a human.

HOW MANYThe scenario decides the count, not a setting

There is no fixed "N test cases per scenario". Each scenario ends with a numbered Conditions to cover list, and the generator writes exactly one test case per entry — so a thin scenario gets one and a six-field family gets six. GUARDRAILSWhat stops a thread

Threads are cheap to start and expensive to leave running. Four limits bound them, and every one of them returns the work done so far rather than discarding it.

GROUNDINGTwo optional settings that keep the domain language right

Both are optional — leave them empty and nothing changes. Set them once per story family and two whole classes of wrong output disappear.

Setting What it does Simple example
domainhints A one-line glossary handed to all three agents, telling them what each business term maps to. The agents must use these mappings exactly, and the reviewer fails any test case that contradicts them. Eligibility Date = Loop 2000 DTP*356. Assessment Date = Loop 2300 HD03. Maintenance Date = Loop 2000 DTP*303.
bannedterms Words that must never appear in the output. The tool checks this itself — no model judgement — and a hit fails the batch before review. Whole-token match, so banning DTP03 never fires inside DTP*303. ["DTP01", "DTP02", "DTP03"]

Why they exist: an early run invented element names like "Loop 2000 DTP01" for dates the story never describes that way. The hints teach the right names; the banned list mechanically blocks the wrong ones. In a later run the reviewer used the hints to catch a test case calling DTP*348 the "Effective Date" — a real mapping defect, quoted and flagged for a human.

READING ITQuestions people ask first

Plain answers, no jargon.

What is a "thread"?

One scenario, doing its own work. Seven scenarios means seven threads, all going at the same time. Each one writes its test cases, gets them checked, and fixes them if needed — without waiting for the other six. That is why the whole run takes as long as the slowest thread, not all seven added together.

Why does nothing happen for the first 63 seconds?

Two jobs have to finish before there is anything to split up: reading the story from Azure DevOps (under a second), and turning it into seven scenarios, each with its numbered conditions list (about a minute). Only then does the work fan out. That first minute is the same whether you ask for two scenarios or ten.

What is a repair round?

The reviewer said one or more of the scenario's test cases were not good enough, so the thread writes them again — this time it is told exactly what was wrong. In the measured run, four of the seven threads needed one. Two came back better and passed (85→92, 85→95); two did not and shipped flagged. A repair costs one to two more minutes, which is why the lanes that needed one finish so much later.

One lane scored 85, then 85 again, and stopped. Why?

Any failing test case pins the batch score at 85, so the score alone says little — the thread also counts how many cases pass each round. If neither number improves, trying a third time almost never helps, so the thread gives up instead of spending another two minutes. Its test cases are still in the output, marked for someone to look at.

What if a repair makes things worse?

It happens — a regeneration can come back with fewer passing cases than the round it was meant to fix. The thread keeps a snapshot of its best reviewed round and ships that one, logging step=keptbest. A repair round can waste two minutes, but it can never destroy work. The same rule covers a final round that errors outright: the scenario ends "unhealed" with its best table intact, never empty.

"19 of 22 ready" — are the other three missing?

No. You always get all 22. "Ready" means the reviewer had no objection and you can hand it to a tester as it is. The three that are not ready are in the same file, each with a note saying what the reviewer did not like — in this run, two call DTP*348 the "Effective Date" where the domain hints say Eligibility Date, and one covers too few of its scenario's listed conditions. It is a second opinion, not a filter.

Why is the review bar so much shorter than the writing bar?

Writing a scenario's test cases takes a while — 63 to 145 seconds. Reading them and giving a verdict takes 15 to 26. Writing is where nearly all the time goes, which is also why the threads matter: it is the writing that runs seven ways at once.

Would more scenarios make it slower?

Barely. Six scenarios and seven scenarios both take about five minutes, because they run side by side. What does make it slower is repairs — each one adds a full round of writing and reviewing to that one lane.

STAYING SMALLFive things that keep the payloads down

The first version of this pipeline sent everything in one call and kept dying. Each of these is measured, and each one bought back time or headroom.

01 The generator writes nested JSON, not a table. In the 13-column table, nine columns repeat identically on every step row — 65% of all characters were the same text over and over. Writing each test case once, with its steps as a list, and letting the tool build the table cut what the model has to produce from 27,819 characters per scenario to 15,724. Flat JSON would have been 36% worse than the table, because it repeats the key names instead. −43%
02 The finished table never goes back through an agent. It is printed to the log; the answer carries a pointer to it. Returning it meant the calling agent had to retype 53,000 tokens it already had — about fifteen minutes of doing nothing useful. 42× smaller
03 One scenario per call. Each generate call carries roughly 28 KB instead of all seven scenarios at once. The single-call version produced 124 KB in one response and the connection kept dropping. Smaller calls are also what makes them safe to run in parallel. 4× smaller
04 A repair is told which test cases are broken. The reviewer returns a verdict per test case, so the repair round gets the failing ids and the exact quoted evidence — not a single score for the batch and a request to start over. targeted
05 Submit, then poll. No request is held open while an agent thinks. The longest single call in this run took 227 seconds and returned normally, because the tool asked for the result rather than waiting on the line. no timeouts
